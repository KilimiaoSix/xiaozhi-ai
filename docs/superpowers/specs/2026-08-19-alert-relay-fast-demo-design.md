# 告警诊断快速演示模式设计

日期：2026-08-19
状态：已实现
Scope：`server`

## 目标

飞书点击「帮我查」后，演示环境应尽量在 60 秒内得到一张简短但真实的诊断卡片，
同时保留现有完整深度诊断能力。

## 方案

为 `ClaudeCodeRunner` 增加可配置的 `fast_mode`，代码默认值为 `true`：

- 快速模式不启动 Claude Code，由 Server 直接执行仓库内 `sae_logs.py`，
  只做一次 SAE 日志查询，时间窗为告警时间前后 5 分钟。
- 不读业务源码，不追查 taskId 生命周期，不读取配置或 git 历史。
- Server 使用 55 秒硬超时，其中单次 HTTP 查询最多 30 秒，为卡片渲染预留时间。
- Server 根据相关日志数、原始关键词命中数、成功/异常标记、实际 Pod 与告警 Pod
  生成 `title / root_cause / user_impact / suggestion`。
- 有相关日志但原始告警关键词未出现时，结论固定为“告警未被窗口日志佐证”，
  明确列出反证并提示旧 Pod、规则延迟或回放数据，不再写笼统的“证据不足”。
- 日志命令认证、网络或执行失败时直接返回 `FAILED`，不能伪装成业务诊断成功。
- `fast_mode: false` 时沿用现有完整 skill 流程和完整 JSON 契约。

## 配置与兼容性

`alert_relay.diagnosis` 新增：

```yaml
fast_mode: true
timeout_seconds: 55
```

快速模式是 runner 和当前配置的默认行为；显式设置 `fast_mode: false` 并恢复较长超时
即可启用深度模式。快速模式不要求 Claude CLI；两种模式共用 SAE 凭证和跨平台
`sae_logs.py`，深度模式继续使用只读工具白名单。

## 数据流

1. Server 根据 `fast_mode` 选择直接日志查询或 Claude Code 深挖。
2. 快速模式执行一次 `sae_logs.py`，并在 Server 内做确定性计数与 Pod 对比。
3. 汇总结果转成 `Diagnosis`，继续复用飞书卡片和机器人播报逻辑。
4. 深度模式保持原有 skill 提示词、JSON 解析和完整诊断契约。

## 失败处理

- 55 秒内无输出：终止子进程，状态为 `FAILED`，不留下孤儿进程。
- SAE 401/403、网络失败或脚本异常：保留脚本错误并落为
  `FAILED`；不把认证失败描述成业务根因。
- JSON 缺少 `title` 或 `root_cause`：仍按现有契约判失败。

## 验收标准

1. 快速模式直接执行一次精确日志查询，禁止源码/git/taskId 深挖。
2. 配置工厂能把 `fast_mode` 和 55 秒超时传给 runner；health 能展示当前模式。
3. 深度模式提示词和行为保持兼容。
4. 单元测试覆盖快速汇总、深度提示词、配置装配与超时杀进程。
5. 使用真实生产 token 运行快速演示链路，60 秒内进入 `DIAGNOSED`；结论必须包含
   日志数量、原始关键词命中和 Pod 对比，不能只写“证据不足”。

## 非目标

- 不增加后台二阶段深度诊断。
- 快速模式不推断代码级业务根因，只做日志一致性判定；代码级根因留给深度模式。
- 不改变 SAE 接口、飞书回调接口或状态机。
- 不提交、推送或创建 PR。
