# 飞书每日关注晨报技术方案

## 1. 需求分析

每天上班前，用户需要从自己有权查看的 飞书消息和当天日程中快速识别最需要处理的三件事。

晨报应优先覆盖直接 `@我`、仍未回应的请求、生产阻塞、当天截止事项、待回复邀请和冲突日程，并保留可核验的来源定位。

由于开放接口不提供客户端逐会话已读游标，本能力统一描述为“待关注/未处理”，不复刻或声称等同客户端未读角标。

第一阶段只提供只读预览和最近一次结果查询，不主动发送消息，也不代替用户确认、回复或修改日程。

## 2. 整体思路

三个核心问题如下。

第一，如何尽量完整地找到用户需要关注的消息？使用用户授权令牌分别执行时间窗内的全量可见消息搜索和 `@我` 搜索，并逐页拉取；两路结果按消息 ID 合并，避免单一路径遗漏。

第二，如何把大量信息压缩成可信的三件事？先用固定规则评分、识别同一话题和后续本人回复，再优先选择不同话题；生成结果始终带来源定位，语言模型不参与候选删选。

第三，如何让结果可持续且可解释？本地台账只保存标识、短摘要和处理状态，重复扫描不会重复创建；每次输出同时给出各数据源页数、条数、失败原因和整体覆盖状态。

```text
HTTP 预览请求
   → ① 计算扫描时间窗
   → ② 并行拉取可见消息、@我消息、当天日程
   → ③ 逐页校验、归一化、按消息 ID 去重
   → ④ 写入本地关注台账并识别本人后续回复
   → ⑤ 固定规则评分并选择 Top 3
   → ⑥ 保存预览和完整覆盖说明
```

## 3. 关键设计权衡

### 3.1 如何定义“未读”

#### 方案 A：模拟客户端未读角标

根据扫描时间或本地访问时间推断哪些消息可能尚未阅读。

利：

- 用户看到的名称与客户端习惯接近
- 展示逻辑简单

弊：

- 开放接口没有用户逐会话已读游标，推断结果无法证明
- 容易把已在客户端阅读的消息再次标成未读

#### 方案 B：定义为开放关注项

按新发现、直接 `@我`、请求、截止时间、后续本人回复和手工状态维护关注项。

利：

- 每个状态都有可解释证据
- 不依赖客户端未公开的读游标
- 后续获得正式未读接口时可以平滑增加独立维度

弊：

- 与客户端未读数不会完全一致
- 首次扫描需要用户校准关注范围

**结论**：在现有开放能力下，方案 B 能保持结果真实可解释；界面必须明确写“待关注/未处理”。

### 3.2 采集完整性如何保证

#### 方案 A：仅依赖机器人事件

机器人加入群后实时接收消息事件并生成晨报。

利：

- 实时性高
- 日常增量成本低

弊：

- 机器人当前不在用户全部会话中
- 无法覆盖用户私聊和机器人不可见的群
- 事件丢失后难以补齐

#### 方案 B：用户身份定时搜索

使用用户令牌按时间窗分别搜索全部可见消息和 `@我` 消息，完整消费分页。

利：

- 覆盖范围与授权用户实际可见范围一致
- 支持重扫、重试和十分钟重叠去重

弊：

- 依赖 `search:message` 等用户权限
- 搜索与详情接口在私有部署中的支持度需要持续验证

#### 方案 C：搜索为主、事件校验

定时搜索负责完整性，机器人事件只用于降低延迟和交叉校验。

利：

- 同时兼顾完整性和实时性
- 可检测部分事件或搜索异常

弊：

- 系统状态与去重路径更复杂
- 第一阶段无法从零机器人会话中获得额外收益

**结论**：第一阶段倾向方案 B；未来机器人覆盖提升后，可在不改变台账和排序的情况下演进到方案 C。

### 3.3 是否保存完整消息正文

#### 方案 A：保存完整正文

把搜索结果正文全部存入数据库，后续直接重算晨报。

利：

- 离线重算方便
- 能保留更多上下文

弊：

- 扩大个人消息泄露风险
- 内容留存和权限撤销后的处理成本高

#### 方案 B：只保存短摘要和标识

完整正文只在当前进程内用于归一化，台账持久化消息 ID、话题 ID、短摘要、来源定位和状态。

利：

- 符合最小必要采集原则
- 数据泄露影响范围更小

弊：

- 历史重算只能依赖短摘要或重新拉取
- 来源消息删除后上下文可能不足

**结论**：个人通信内容敏感，方案 B 更符合当前演示和上线边界；短摘要默认上限 240 字符，七天后清空。

### 3.4 日历权限拿不到时怎么办

2026-08-18 实测确认：i讯飞不发放 `calendar:calendar:readonly`，因此改用正版飞书（`open.feishu.cn`），该权限在飞书上可正常申请并已实测通过。日程原本是排序的输入之一（当天截止、待回复邀请、冲突日程），必须决定缺了它怎么表现。

#### 方案 A：照常请求，失败即失败

保持三路采集，日历失败进入覆盖说明。

利：

- 代码不动，权限一旦发放立即生效

弊：

- 每天都产生一条永久 `FAILED`，整体状态永远停在 `PARTIAL`
- 真正的偶发故障被这条常驻噪声淹没，覆盖说明失去预警价值

#### 方案 B：配置显式关闭

`calendar_enabled: false` 时根本不发起日历请求，该源覆盖状态记为 `DISABLED` 且不参与整体评价。

利：

- `PARTIAL` 重新只表示真实异常，覆盖说明可信
- `missing_scopes` 不再混入拿不到的权限，排查时不会被误导
- 权限一旦发放，改一个开关即可恢复三路

弊：

- 多一个配置维度
- 关闭期间排序失去日程信号，Top 3 仅由消息产生

**结论**：采用方案 B。关键是把「主动关闭」和「调用失败」区分开——两者都表现为没有日历数据，但只有后者需要有人去查。

### 3.5 晨报什么时候送到人面前

只读预览要人主动去桌面端点一下，而最需要晨报的时刻恰好是刚坐下、还没打开电脑的那一分钟。这一步要决定由谁来发起。

#### 方案 A：固定时刻定时调度

工作日 08:45 定时扫描并播报。

利：

- 实现最简单，一个定时器即可
- 到点必发，行为可预期

弊：

- 人不在工位时对着空椅子播一遍，当天就没有第二次了
- 早到和晚到的人都对不上，固定时刻只服务作息最规律的那一类

#### 方案 B：摄像头认出主人时触发

工作日 08:00–09:30 窗口内，`PresenceRegistry` 第一次出现 `present + owner` 时扫描并播报，每天一次。

利：

- 播报时人一定在工位，且是本人——这两件事已由人脸核验保证
- 早到晚到都对得上，不需要用户配置自己的作息
- 复用既有在岗链路，不引入新的外部触发源

弊：

- 摄像头没开或人脸未录入时当天不播
- 「第一次」的语义要额外定义（见下）

**结论**：采用方案 B。语义定为「**窗口内**的第一次」而不是「当天的第一次」——7:50 就到工位的人在 8:00 一样该听到晨报，否则来得早反而没有。

同一时刻工位上还有另一条链路：`presence_robot` 的到岗迎接。它是事件驱动的，比轮询的晨报早几秒，而设备的音频通道独占——两条推送叠在一起时，晨报会被 `push_work_event` 判定为「设备正在播放语音」而降级成只上屏，等于白播。所以晨报在扫描前先看设备忙不忙，忙就等下一次轮询；忙满 `busy_grace_seconds` 才照发（只上屏也比今天不播强）。没有把晨报塞进迎接语里合并成一条推送，是因为迎接要立刻说出口，而扫描要等飞书返回，合并会把迎接拖慢好几秒。

### 3.6 播报里放多少内容

预览报告是给桌面端看的：Top 3 带 240 字摘要、其他提及、完整日程、逐源覆盖说明。机器人只有一块小屏和一条 TTS 通道，整份念完要一分多钟，早上没人会听完。

因此播报只保留**按优先级排好的前三条待办**，每条截断到 16 字，其余未处理提及折成数量，日程项前缀开始时间。实测一条完整晨报约 75 字。

排序不在播报层做：`top_three` 已经是 `ranking.py` 按分数排好的顺序，播报层只负责编排文案，保证念出来的第 1 条就是最该先处理的那条。

覆盖状态不是 `COMPLETE` 时补一句「数据可能不全。」——采集缺了一路却照常念完，会让人以为待办就这些。

时间窗、生效星期、开场称呼、状态栏文案、表情和条数都走配置，不写死在代码里：同一台机器人换个工位，作息和称呼就是使用者的事。唯一不跟着配置走的是授权过期/缺权限那条通知——它是故障提示不是晨报，套上「早报」的状态栏会让人误以为今天没有待办。

## 4. 改动清单

### 4.1 新增的能力

#### 飞书只读采集

服务端可使用用户授权令牌拉取指定时间窗内的可见消息、直接 `@我` 消息以及当天展开后的日程实例，并完整处理分页。

#### 本地关注台账

同一消息重复扫描时只保留一条记录；新发现、跨日携带、已回复、延后、完成和忽略状态可持续保存，完整正文不落库。

#### 每日 Top 3 与覆盖说明

预览按确定性规则产出三项优先事项、其他未处理提及、日程冲突和各来源采集状态；单源失败时明确标记部分覆盖。

#### 只读 HTTP 接口

新增手工预览、最近一次结果和能力健康检查，复用现有 HTTP Bearer 鉴权。

#### 在岗触发的晨报播报

工作日 08:00–09:30 窗口内，绑定工位第一次出现 `present + owner` 时执行一次扫描，把前三条待办压成一句话推给机器人并播报，每工位每天一次。机器人不在线时不发起扫描，只在窗口内隔一个重试间隔再看设备回来没有；扫描或推送连续失败到上限就放弃当天，不在早高峰每分钟重试一次飞书。

### 4.2 调整的逻辑

#### HTTP 服务启动

主 HTTP 服务启动时注册晨报路由并初始化本地台账；默认配置关闭晨报，不影响未配置用户令牌的现有部署。拿得到设备注册表时（即与 WebSocket 服务同进程）额外拉起播报轮询任务，随 aiohttp 应用启停。`presence_server.py` 那个轻量入口没有设备注册表，不装配播报器，晨报保持只有 HTTP 预览入口的行为。

### 4.3 不动的部分

- 设备 WebSocket 连接和机器人动作协议不变。
- 现有 OTA、视觉、事件推送和 presence 接口不变。
- 不创建或修改任何 飞书消息、群、日程和审批。
- 不增加主动消息发送、定时任务或交互卡片回调。

## 5. 已知 issue / 待决策

### 5.1 用户授权（已解决）

问题：初期应用缺少 `search:message`、用户消息读取和日历读取权限，且本机没有有效用户 OAuth 会话。

影响：代码只能完成模拟服务和契约测试，无法宣称真实数据已拉取成功。

处理：2026-08-18 已在正版飞书应用上开通全部五项权限并完成 OAuth，真实联调通过，消息、`@我` 和日历三路覆盖状态均为 `COMPLETE`。注意权限变更后必须重新签发令牌，旧令牌不会自动获得新权限。

### 5.2 私有部署的消息详情接口兼容性

问题：消息搜索存在，但详情读取是否接受用户令牌需要真实权限后验证。

影响：若搜索只返回消息 ID 且详情接口拒绝用户令牌，预览只能报告消息来源部分失败，不能生成可信摘要。

处理：第一阶段客户端会优先使用搜索结果中的详情，再尝试批量详情接口；失败明确标记为部分覆盖。后续可升级 CLI/MCP 或增加更窄的内部读取适配器。

### 5.3 节假日工作日历

问题：首版只识别周一至周五，未接入公司调休表。

影响：调休周末或法定节假日前后的首次扫描窗需要手工指定日期复核。

处理：接受。真实排期阶段再接入组织工作日配置。

## 6. 回滚策略

### 6.1 紧急停用

将 `morning_brief.enabled` 设为 `false` 并重启服务，三个晨报接口保留但返回禁用状态，播报轮询也不会装配；其他 HTTP 和 WebSocket 能力不受影响。只想停掉早上的主动播报、保留手工预览时，改 `morning_brief.announce.enabled` 为 `false` 并重启。

### 6.2 外部接口兼容性异常

保持本地台账不变，关闭晨报采集，回退到上一个服务版本；由于外部操作全部只读，不需要撤销 飞书侧数据。

### 6.3 本地台账异常

停用能力后备份并移走 `data/morning_brief.sqlite3`，服务下次启用时会重建空台账。删除台账会丢失本地关注状态和水位，但不会影响源消息和日程。

### 6.4 排序结果异常

关闭预览入口或回退版本；确定性规则不写回外部系统，已保存的预览只用于本地查询，不产生不可逆副作用。

## 附录 A：数据模型

关注项保存消息 ID、会话/话题 ID、发送者 ID、提及类型、首次/最近发现时间、源时间、状态、分数、短摘要和来源定位。完整消息正文不进入 SQLite。

预览保存报告日期、生成时间、扫描窗口、Top 3、其他提及、日程与冲突、来源覆盖状态。水位独立保存，仅在两路消息分页全部成功并完成持久化后推进。

## 附录 B：接口与代码文件

- `POST /xiaozhi/morning-brief/preview`：执行一次只读扫描并保存预览。
- `GET /xiaozhi/morning-brief/latest`：返回最近一次已保存预览。
- `GET /xiaozhi/morning-brief/health`：返回开关、凭据配置状态、必要权限和外部能力说明，不返回令牌。
- `core/morning_brief/`：领域模型、排序、私有 OpenAPI 客户端、SQLite 台账和聚合服务。
- `core/morning_brief/announcement.py`：把报告压成一句话的纯函数，不做任何 I/O。
- `core/morning_brief/announcer.py`：在岗触发、每日一次、失败退避的播报轮询。
- `core/api/morning_brief_handler.py`：Bearer 鉴权、请求校验和 JSON envelope。
- `core/morning_brief_routes.py`：aiohttp 路由注册。
