# 飞书每日关注晨报接口

编码 Agent 为同组织新成员自动配置本能力时，先阅读 [飞书每日关注晨报 Agent 初始化手册](飞书每日关注晨报-Agent初始化手册.md)。该手册包含现有应用信息、Computer Use 安全边界、OAuth、凭证落盘和验收步骤。

## 1. 能力边界

本模块通过飞书开放平台的用户身份 OpenAPI，聚合指定时间窗内用户可见的消息、直接 `@我` 消息和当天日程，生成最多三条优先关注项。

开放接口不提供用户逐会话已读游标或客户端未读角标，因此接口只返回“待关注/未处理”，不代表飞书客户端真实未读。模块只读取外部数据，不发送消息、不修改日程、不代替用户回复。

## 2. 前置权限

本模块不绑定任何特定应用，接入方在自己的飞书租户里用**任意一个自建应用**即可。换一台机器接入只需要做两件事：**给应用开通下列权限**，**签发一个带这些权限的用户令牌**。

应用后台和用户 OAuth 都需要具备以下权限：

```text
search:message                     获取消息搜索结果
im:message:readonly                获取单聊、群组消息
im:message.p2p_msg:get_as_user     以用户身份获取单聊消息
im:message.group_msg:get_as_user   以用户身份获取群聊消息
calendar:calendar:readonly         仅日历源需要
```

前四个是消息源的必需权限，缺任意一个消息源都无法工作。`calendar:calendar:readonly` 只在启用日历源时需要，拿不到就把 `calendar_enabled` 置为 `false`，日历一路记为 `DISABLED`，不影响消息源和整体覆盖状态。

`POST /open-apis/search/v2/message` 只返回 `message_id`，消息内容、发送人和时间必须再调 `GET /open-apis/im/v1/messages/mget` 补齐。用户令牌读消息详情**必须同时具备基础权限和按会话类型的补充权限**：`im:message:readonly` 只是基础权限，单聊和群聊各需一个 `get_as_user`，缺任意一个会让对应会话的消息读不到。

权限在开发者后台开通后需**发布新版本并经管理员审批**才生效，且**已签发的令牌不会自动获得新权限**，必须重新走一次 OAuth。加了权限却仍报 `99991679 应用未获取所需的用户授权` 时，先检查令牌是不是加权限之前签发的。

`missing_scopes` 只返回**已启用数据源**真正需要的权限，关闭日历源时不会混入日历权限。

实测记录（2026-08-18，域 `open.feishu.cn`；应用 `cli_a9383f818e3a5bef` 仅为本次实测所用，接入方换成自己的即可）：

| 接口 | 令牌 | 结果 |
| --- | --- | --- |
| `POST /open-apis/search/v2/message` | user | 成功，返回**字符串 `message_id` 列表**，不含正文 |
| `POST /open-apis/search/v2/message` | tenant | 不支持，该接口只接受用户令牌 |
| `GET /open-apis/im/v1/messages/{id}` | user（含全部四个消息权限） | 成功 |
| `GET /open-apis/im/v1/messages/mget` | user（含全部四个消息权限） | 成功，批量可用 |
| `POST /open-apis/calendar/v4/calendars/primary` | user（含日历权限） | 成功 |

两个和官方文档不一致、以实测为准的点：

- **时间窗字段是 `start_time` / `end_time`，单位为秒。** 传成 `from_time` / `to_time` 不会报错，接口会静默忽略时间窗并返回全部历史消息；传毫秒时间戳则返回空结果。
- **`at_chatter_ids` 只接受 `open_id`。** 官方文档写的是「at 用户 user_id 列表」，实际传 `user_id` 返回 `99992351 not a valid {open_id}`。

消息搜索无法用 tenant token 兜底，用户访问令牌是硬要求；令牌缺失时预览返回 `reauthorization_required: true`。

外部请求固定使用：

```text
https://open.feishu.cn
POST /open-apis/search/v2/message
GET  /open-apis/im/v1/messages/mget
POST /open-apis/calendar/v4/calendars/primary
GET  /open-apis/calendar/v4/calendars/{calendar_id}/events/instance_view
```

### 2.1 开通与授权步骤

从零到能联调，按顺序走完这六步。前两步在飞书开发者后台完成，后四步在本机。

**第一步：开通权限。** 进入应用的「权限管理」，用上面的 scope 字符串逐个搜索并开通。四个消息权限是必需的，日历权限按需。

**第二步：发布版本。** 权限变更必须发布新版本并经管理员审批才生效，只在后台勾选不发版不会生效。

**第三步：登记回调地址。** 进入「安全设置 → 重定向 URL」，添加第五步 OAuth 要用的回调地址。飞书**精确匹配**协议、端口和路径，少一个字符都会被拒。用 `lark-mcp` 签发令牌时固定是：

```text
http://localhost:3000/callback
```

自己实现授权流程则填自己的回调地址。

**第四步：确认权限已生效。** 在开发者后台的权限管理页核对五个 scope 的状态，并确认包含这些权限的应用版本已发布且审批生效。

**第五步：签发用户令牌。** 这一步是标准的飞书用户身份 OAuth，与本模块无关，用任意方式完成都可以，浏览器授权环节需要人工点确认。

标准流程是两步：先让用户在浏览器打开授权页（`redirect_uri` 必须与第三步登记的完全一致），拿到 `code`；再用 `code` 换取 `user_access_token`。

```text
GET  https://open.feishu.cn/open-apis/authen/v1/authorize
       ?app_id=<app_id>
       &redirect_uri=<已登记的回调地址>
       &scope=<空格分隔的 scope 列表>
POST https://open.feishu.cn/open-apis/authen/v2/oauth/token
```

若本机装了 `lark-mcp`，它把上面两步封装成了一条命令，会临时起一个本地回调服务：

```bash
lark-mcp login -a <app_id> -s <app_secret> \
  -d https://open.feishu.cn \
  --scope "search:message im:message:readonly \
           im:message.p2p_msg:get_as_user im:message.group_msg:get_as_user \
           calendar:calendar:readonly"
```

无论用哪种方式，**每次新增权限后都要重跑这一步**，旧令牌不会自动获得新权限。签发的令牌有有效期，过期后同样要重新签发。

**第六步：取 open_id 并联调。** 用刚签发的令牌换取当前用户的 `open_id`：

```bash
curl https://open.feishu.cn/open-apis/authen/v1/user_info \
  -H "Authorization: Bearer <user_access_token>"
```

把令牌和 `open_id` 写入被 Git 忽略的 `server/main/xiaozhi-server/data/.env`：

```dotenv
FEISHU_USER_ACCESS_TOKEN=<user_access_token>
FEISHU_SELF_OPEN_ID=<current_user_open_id>
```

也可以直接设置同名进程环境变量；进程环境变量优先于 `data/.env`。然后用仓库内的联调脚本一次性验证三个接口：

```bash
cd server/main/xiaozhi-server
FEISHU_USER_ACCESS_TOKEN=<token> FEISHU_SELF_OPEN_ID=<open_id> \
  python run_morning_brief_check.py
```

脚本会起一个临时服务，依次调用 `health`、`preview`、`latest` 并打印真实返回。判断标准是 `coverage_status` 为 `COMPLETE`、各数据源 `status` 均为 `COMPLETE`。

### 2.2 常见错误码

| 错误码 | 出现位置 | 含义与处理 |
| --- | --- | --- |
| `20029` | 授权跳转 | 重定向 URL 未登记或不完全匹配，检查安全设置里的协议、端口和路径 |
| `20043` | 授权跳转 | 请求了应用未开通的 scope。响应与请求一个不存在的 scope 完全相同，无法区分「没申请」和「平台没有该权限项」 |
| `99991668` | 任意接口 | 令牌无效或未附带 |
| `20092` | 任意接口 | 令牌与调用域不匹配，例如拿私有化部署的令牌调 `open.feishu.cn` |
| `99991679` | 日历接口 | 令牌缺少日历权限。权限已开通仍报此错时，多半是令牌在开通之前签发的，重走 OAuth |
| `230027` | `im/v1/messages*` | 缺少按会话类型的 `get_as_user` 补充权限 |
| `99992351` | 搜索接口 | `at_chatter_ids` 传了非 `open_id` 的值 |

## 3. 配置

默认配置关闭晨报。不要把用户令牌提交到 `config.yaml` 或 `data/.config.yaml`，应写入被 Git 忽略的本地 `data/.env`，也可以通过同名进程环境变量覆盖。

PowerShell 环境变量示例：

```powershell
$env:FEISHU_USER_ACCESS_TOKEN = "<user_access_token>"
$env:FEISHU_SELF_OPEN_ID = "<current_user_open_id>"
```

本地 env 文件示例：

```dotenv
FEISHU_USER_ACCESS_TOKEN=<user_access_token>
FEISHU_SELF_OPEN_ID=<current_user_open_id>
```

`data/.config.yaml` 非敏感配置示例：

```yaml
morning_brief:
  enabled: true
  base_url: https://open.feishu.cn
  # 没有 calendar:calendar:readonly 时置为 false，日历源记为 DISABLED，
  # 不会把整体覆盖状态拖成 PARTIAL。
  calendar_enabled: true
  timezone: Asia/Shanghai
  ledger_path: data/morning_brief.sqlite3
  page_size: 50
  max_pages: 40
  timeout_seconds: 15
  overlap_minutes: 10
  excerpt_chars: 240
  excerpt_retention_days: 7
  resolved_retention_days: 30
  announce:
    enabled: true
    window_start: "08:00"
    window_end: "09:30"
    workdays: [1, 2, 3, 4, 5]
    greeting: "早上好"
    status: "早报"
    emotion: happy
    max_items: 3
    item_chars: 16
    retry_seconds: 60
    max_attempts: 3
    busy_grace_seconds: 120
    poll_seconds: 5
    restore_after_seconds: 20
    bindings:
      - workstation_id: desktop-local
        device_id: ""
```

OAuth 回调地址需要预先登记在应用的「安全设置 → 重定向 URL」白名单里，精确匹配协议、端口和路径，否则授权返回 `20029 重定向 URL 有误`。

若 `server.auth.enabled: true`，调用下面所有接口都必须携带：

```http
Authorization: Bearer <server.auth_key>
```

此 Bearer 值是 launchcrush HTTP 服务鉴权密钥，不是飞书用户令牌。

### 3.1 在岗触发的晨报播报

`announce` 段控制「早上第一次认出主人就播晨报」这条链路。它没有独立 HTTP 接口：触发源是 `PresenceRegistry`，出口是设备 WebSocket 的 `alert`（外加一次 TTS），扫描仍走本文档 §4 的同一段服务代码，结果同样落台账，可用 `GET /xiaozhi/morning-brief/latest` 复查刚才播的是什么。

同时满足下列条件才播，每个工位每天一次（播报标记落在台账 SQLite 里，改配置重启进程也不会当天重播）：

- `morning_brief.enabled` 和 `announce.enabled` 都为真（前者关着时连扫描都不会发生）；
- 当天是 `workdays` 之一（ISO 星期，1 为周一），本地时间落在 `[window_start, window_end)`；
- 该工位的最新在岗快照是 `effective_state=present` 且 `identity.state=owner`——陌生人、`no_face` 和上报断流派生出的 `stale` 都不算；
- 绑定的机器人在线。`device_id` 留空时只在**恰好一台**设备在线的情况下自动绑定，避免多台时猜错。

判定的是「**窗口内**的第一次」而不是「当天的第一次」：8 点前就坐在工位上的人，窗口一打开同样会收到晨报。

与 `presence_robot` 的到岗迎接是两条独立链路：迎接是事件驱动的，会先说一句；晨报是轮询的，比它晚几秒。设备的音频通道独占，所以播报前会先看设备忙不忙，忙就等下一次轮询——否则 `push_work_event` 会把这次播报降级成只上屏。想避免连着听到两句「早上好」，把 `greeting` 置为空串即可。

设备收到的 `alert` 形如：

```json
{
  "type": "alert",
  "status": "早报",
  "message": "早上好，今天 3 件待办：1 线上支付回调失败，麻烦今天先回滚…；2 排期表我更新了，需要你确认一下下…；3 10:00 迭代评审。另有 2 条待回。",
  "emotion": "happy",
  "silent": false,
  "session_id": "<current session id>"
}
```

文案规则：编号顺序就是 `top_three` 的优先级顺序，日程项前缀开始时间（按 `morning_brief.timezone` 的钟面念，海外组织者建的会不会照抄它自己的时区）；每条按 `item_chars` 截断（超出补 `…`）；其余未处理提及只报数量；`coverage_status` 不是 `COMPLETE` 时补一句「数据可能不全。」——包括待办为空的时候，避免采集缺了一路却让人以为待办就这些。正常晨报在 `restore_after_seconds` 秒后把画面还给设备基态（配 `0` 则不收屏）；故障通知一律常驻屏幕。

可改的文案与时间参数：

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `window_start` / `window_end` | `08:00` / `09:30` | 本地时间窗，左闭右开；配的是新窗口而不是叠加在默认窗口上。必须带引号写 `"HH:MM"`，不带引号会被 YAML 当数字；解析不了或写反的窗口回退默认并打警告日志 |
| `workdays` | `[1,2,3,4,5]` | ISO 星期，1 为周一；配成 `[1,2,3,4,5,6,7]` 则每天都播 |
| `greeting` | `早上好` | 开场称呼，出现在待办和「今天暂时没有待办」两种文案里；置为空串则不问好 |
| `status` | `早报` | 设备状态栏文案 |
| `emotion` | `happy` | 固件表情名，Server 不校验枚举；固件不认识的名字只显示文字 |
| `max_items` / `item_chars` | `3` / `16` | 播几条、每条多少字；`max_items` 同步作为扫描的排序条数，调大就真的多念几条 |

授权过期或缺权限时的那条通知不套用 `status` / `emotion`：它是故障提示不是晨报，把「早报」留在屏幕上会让人以为今天没有待办。这几项都在进程启动时读入，改完要重启服务。

失败时的行为：

| 情况 | 行为 |
| --- | --- |
| 机器人不在线 | 不发起飞书扫描，`retry_seconds` 后在窗口内重试，不计入尝试次数 |
| 设备正忙（到岗迎接的 TTS 在放、用户在说话） | 不发起扫描，下次轮询再看；忙满 `busy_grace_seconds` 后照发，接受降级为只上屏 |
| 扫描期间设备转忙或断线重连 | 送达前按 `device_id` 重取连接并复查忙态；语音被挤掉时画面已上屏，宽限内 `retry_seconds` 后静默补播语音（不再扫飞书、不再响提示音），宽限用尽接受只上屏 |
| 三路采集全部失败（断网、飞书接口异常） | 不会播「今天暂时没有待办」，按扫描失败改期重试，累计到 `max_attempts` 放弃当天 |
| 扫描或推送异常 | 记一次尝试，`retry_seconds` 后重试；累计到 `max_attempts` 就放弃当天 |
| `reauthorization_required` / `permission_required` | 只在屏幕上显示一句不可用说明（含 token 未配置的情况），不做 TTS 播报，常驻屏幕不自动收走 |

关掉这条链路把 `announce.enabled` 置为 `false` 即可，三个 HTTP 接口不受影响。

真机验收不必等到早上八点。对着已经在跑的 Server 执行：

```bash
cd server/main/xiaozhi-server
python run_morning_brief_announce_check.py
```

脚本先查配置（总开关、播报开关、令牌、当前时间在不在窗口、工位绑定）并把不通过的项逐条列出来，再确认设备在线，然后打一条 `present + owner` 的在岗上报模拟主人坐下，最后轮询 `latest` 等这次扫描的新报告，把机器人应该念的那句话打印出来供比对。想在非窗口时段验收，把 `window_start` / `window_end` 临时改成覆盖当前时间并重启服务。

## 4. 生成预览

### `POST /xiaozhi/morning-brief/preview`

执行一次只读扫描，更新本地关注台账并保存报告。省略 `report_date` 时使用 `Asia/Shanghai` 当天。

请求：

```json
{
  "report_date": "2026-08-18"
}
```

调用示例：

```bash
curl -X POST http://127.0.0.1:8003/xiaozhi/morning-brief/preview \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <server-auth-key>" \
  -d '{"report_date":"2026-08-18"}'
```

成功响应：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "report_type": "OPEN_ATTENTION",
    "report_date": "2026-08-18",
    "generated_at": "2026-08-18T01:00:00+00:00",
    "scan_window": {
      "start": "2026-08-17T18:00:00+08:00",
      "end": "2026-08-18T09:00:00+08:00"
    },
    "coverage_status": "COMPLETE",
    "coverage": [
      {
        "source": "messages",
        "status": "COMPLETE",
        "pages": 2,
        "item_count": 63,
        "next_page_token_present": false,
        "error": null
      }
    ],
    "top_three": [],
    "other_unhandled_mentions": [],
    "calendar": [],
    "reauthorization_required": false,
    "permission_required": false,
    "missing_scopes": [],
    "disclaimer": "待关注/未处理不等同于飞书客户端真实未读。"
  }
}
```

覆盖状态含义：

- `COMPLETE`：所有**已启用**数据源都完整成功。
- `PARTIAL`：至少一路可用，但另一路失败、分页被截断或部分记录无法归一化。
- `FAILED`：已启用的数据源全部失败，结果只用于诊断，不能作为当天完整晨报。

单个数据源的 `status` 还可能是 `DISABLED`，表示该源被配置主动关闭（当前部署即为日历）。`DISABLED` 不参与整体评价，`error` 恒为 `null`——它是既定配置，不是故障。

当 OpenAPI 返回缺权码 `99991672` 时，`permission_required` 为 `true`，`missing_scopes` 返回应用需要开通并由用户授权的完整 scope 列表。令牌失效则通过 `reauthorization_required` 单独表示。

只有普通消息与 `@我` 两路都为 `COMPLETE` 时，消息高水位才推进。后续扫描从上次成功水位向前重叠十分钟，消息 ID 保证幂等。

常见错误：

- `401 UNAUTHORIZED`：launchcrush HTTP Bearer 鉴权失败。
- `400 INVALID_JSON`：请求体不是合法 JSON。
- `400 MORNING_BRIEF_INVALID_REQUEST`：日期格式或字段不合法。
- `503 MORNING_BRIEF_DISABLED`：配置未启用。
- `502 MORNING_BRIEF_UPSTREAM_ERROR`：服务内部未捕获异常；正常的单源 OpenAPI 失败会进入报告的覆盖说明，不返回 502。

## 5. 查询最近报告

### `GET /xiaozhi/morning-brief/latest`

返回最近一次已保存的报告，不触发外部请求。

```bash
curl http://127.0.0.1:8003/xiaozhi/morning-brief/latest \
  -H "Authorization: Bearer <server-auth-key>"
```

首次预览前返回：

```json
{
  "code": "MORNING_BRIEF_NOT_FOUND",
  "message": "no morning brief preview is available",
  "data": null
}
```

## 6. 健康检查

### `GET /xiaozhi/morning-brief/health`

返回功能开关、用户 ID/令牌是否已配置、所需权限、接口能力和最近报告是否存在。响应不会包含用户令牌。

`capabilities.calendar_enabled` 表明日历源是否启用，`capabilities.required_scopes` 随之变化——关闭日历时不再声明日历权限。

```bash
curl http://127.0.0.1:8003/xiaozhi/morning-brief/health \
  -H "Authorization: Bearer <server-auth-key>"
```

关键状态：

- `DISABLED`：功能开关关闭。
- `CONFIGURATION_REQUIRED`：缺少用户 open_id 或用户访问令牌。
- `PERMISSION_REQUIRED`：最近一次预览收到 OpenAPI 缺权码，需要先在应用后台开通报告中的 `missing_scopes`，再重新进行用户授权。
- `READY`：本地配置齐全，且最近一次预览未发现缺权；首次预览前不代表外部权限已完成验证。

## 7. 本地数据与保留

SQLite 默认位于 `data/morning_brief.sqlite3`。关注项只保存消息 ID、会话/话题 ID、发送者 ID、短摘要、来源定位和状态，不保存完整消息正文。

短摘要默认最多 240 字符，七天后清空；包含短摘要的历史报告也在七天后删除；已完成或忽略记录三十天后删除。要紧急回滚时先将 `morning_brief.enabled` 设为 `false`，再备份并移走 SQLite 文件。移走台账只会丢失本地状态和水位，不会修改源消息或日程。
