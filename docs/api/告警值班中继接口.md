# 告警值班中继接口

## 1. 能力边界

一条 SAE 告警进来后，本模块做四件事：**让机器人抬头提醒人**、**给值班人发飞书卡片**、
**等人回一句话**、**在人点头后调起本机 Claude Code 做只读根因诊断并把结论回帖**。

诊断能力本身不在服务端，而在本机 Claude Code 的 `diagnose-sae-alert` skill 里；
服务端只负责拼提示词、管超时、解析它吐出的 JSON。因此：

- **服务端必须与 Claude Code 跑在同一台机器上**，且那台机器能连内网 SAE。
- 全程只读：只 grep 代码、只读日志、对 SAE 只发 GET，**不改任何线上对象、不自动修复**。
- **人不点头就不开跑。** 状态机不存在「等回复 → 开始诊断」这条边，必须先经过「已认领」。

## 2. 前置条件

### 2.1 飞书机器人权限

用任意一个自建应用即可，需要开通两项权限：

```text
im:message:send_as_bot          以应用身份发消息（发告警卡片、回结论）
im:message.reaction:write       给消息加表情回复（收到回执）
```

事件订阅需要配置**请求地址**指向 `POST /xiaozhi/alert/feishu/callback`，并订阅：

- `im.message.receive_v1` —— 人直接在话题里回一句话时用
- **卡片请求地址**（开发者后台「卡片回调」）—— 人点卡片按钮时用

> **Encrypt Key 必须留空。** 本中继不解密事件；配了加密会收到 `400 ENCRYPTED_EVENT_UNSUPPORTED`，
> 而不是静默丢弃——这是刻意设计，让配错一眼可见。
> Verification Token 填进 `alert_relay.feishu.verification_token` 后会逐条校验。

### 2.2 本机 Claude Code

```bash
claude --version          # 确认 CLI 可用
```

**换一台机器部署时，先看就绪度，别等告警来了才发现缺东西：**

```bash
curl http://127.0.0.1:8003/xiaozhi/alert/health   # data.diagnosis.prerequisites
cd server/main/xiaozhi-server && python run_alert_relay_check.py   # 第 0 步就是依赖自检
```

四项前置里三项是硬性的（缺了直接判失败，不会空转到超时）：

| 检查项 | 缺了会怎样 | 怎么补 |
| --- | --- | --- |
| `claude_cli` | 起不了子进程 | 装 Claude Code；Windows 上写 `claude` 即可，会自动解析 `claude.CMD` |
| `skill` | agent 不知道怎么查 | 仓库自带 `.claude/skills/diagnose-sae-alert/`，正常克隆就有 |
| `sae_credentials` | 拉不到日志 | `export SAE_AUTHORIZATION='Bearer <jwt>'` 或写进 `~/.sae/sae-token.env` |
| `source_dirs`（非硬性） | 只剩日志一条腿，`why.code` 给不出 file:line | 配上被诊断服务的源码目录 |

> **诊断能力随仓库分发，不依赖任何个人机器上的东西。** 这一条是踩过坑的：
> 最初诊断依赖作者个人目录下的 skill 和 Windows 专用的 `sae.ps1`，分支拿到 Mac 上
> 单测和假 CLI 链路都能过，唯独真实诊断**空转到超时才失败**——那种失败看起来像模型慢，
> 实际是依赖压根不存在。现在 skill 和跨平台的
> [`scripts/sae_logs.py`](../../.claude/skills/diagnose-sae-alert/scripts/sae_logs.py)
> 都在仓库里（纯标准库、只发 GET），缺依赖则秒失败并列出缺什么。

Windows 上 npm 装出来的是 `claude.CMD`，服务端用 `shutil.which()` 解析扩展名后再启动，
**配置里直接写 `claude` 即可**，不必写全路径。

子进程以只读方式启动：`--permission-mode dontAsk`，工具白名单
`Read / Grep / Glob / Bash / PowerShell / Skill / TodoWrite`，
**不会传 `--dangerously-skip-permissions`**。

> **`PowerShell` 不能从白名单里删。** skill 是用 PowerShell 工具跑 `sae.ps1` 拉日志的，
> 而 `dontAsk` 会把白名单外的工具直接拒掉。漏掉它不会报错——agent 会一条日志都拉不到，
> 只回一张「什么都查不了」的失败卡片，链路看着通、诊断永远是空的。

`alert_relay.diagnosis.source_dirs` 要填**被诊断服务的源码目录**（如 iflyplot-server），
它会以 `--add-dir` 挂进子进程工作区。不填的话 skill 只剩日志一条腿，多半会如实回「查不了」。

### 2.3 机器人硬件

`alert_relay.robot.device_id` 填目标机器人的 MAC（与 `/xiaozhi/event/devices` 列出的一致）。
留空或设备离线时，飞书那一路照发，卡片上会标注「机器人离线」。

## 3. 接口

| 方法 | 路径 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| POST | `/xiaozhi/alert/ingest` | `server.auth` 的 Bearer | 告警接入 |
| POST | `/xiaozhi/alert/feishu/callback` | verification_token | 飞书事件与卡片回调 |
| GET | `/xiaozhi/alert/{alert_id}` | Bearer | 查单条中继状态 |
| GET | `/xiaozhi/alert/recent?limit=20` | Bearer | 最近的告警列表 |
| GET | `/xiaozhi/alert/health` | Bearer | 依赖就绪度自检 |

响应统一为 `{"code": ..., "message": ..., "data": ...}`；
**飞书回调例外**，它回飞书要的裸 JSON（`challenge` / `toast`）。

### 3.1 POST /xiaozhi/alert/ingest

只有 `raw_text` 必填，其余字段是解析兜底——给了就以给的为准，没给就从原文解析。

```jsonc
{
  "raw_text": "【SAE告警通知】\n告警等级：严重\n告警集群：bj-jxq-autocar\n...",
  "level": "严重",              // 可选，未给则解析；无法解析时默认「警告」
  "cluster": "bj-jxq-autocar",  // 可选
  "namespace": "iflyplot",      // 可选
  "target": "iflyplot-ai-7d9f8b6c5d-x2k9p",  // 可选，pod 名
  "keyword": "无痕改字处理超时",  // 可选，未给则从「包含关键词 X >N条」提取
  "alert_time": "2026-08-18 21:00:11",
  "policy_url": "https://one.iflytek.com/sae/#/alarm?projectId=117&clusterId=3"
}
```

成功返回 `data` 即一条中继记录：

```jsonc
{
  "code": "OK",
  "data": {
    "alert_id": "b3f1a2c4d5e6f708-1787064011",
    "state": "AWAITING_REPLY",
    "deduped": false,
    "repeat_count": 0,
    "alert": { "workload": "iflyplot-ai", "project_id": "117", "cluster_id": "3", ... },
    "robot_delivered": true,
    "feishu_message_id": "om_xxx",
    "warnings": []
  }
}
```

**通知失败不会让接入失败。** 机器人离线或飞书发送报错时仍返回 200，
失败原因写进 `robot_error` / `feishu_error` / `warnings`——告警绝不能因为通知挂了而丢。

`target` 会按 `-<rs hash>-<随机后缀>` 削成 workload，这条规则必须与 skill 一致：
拉日志时 `fields_workload_name` 只认 workload，削错了一条日志都拉不到。

### 3.2 去重

窗口（默认 300 秒）内，**同集群 + 同命名空间 + 同 workload + 同关键词**的告警只累加
`repeat_count`，**不再打扰机器人、不再发新卡片**。pod 名和告警时间刻意不参与指纹计算——
它们每次都变，算进去就永远去不了重，机器人会被告警风暴刷屏。

### 3.3 POST /xiaozhi/alert/feishu/callback

支持四种 body：

| 形态 | 识别方式 | 行为 |
| --- | --- | --- |
| URL 校验 | `type == "url_verification"` | 回 `{"challenge": ...}` |
| 卡片按钮（旧版） | 顶层有 `action` | 按 `action.value.intent` 认领/拒绝 |
| 卡片按钮（v2） | `header.event_type == "card.action.trigger"` | 同上 |
| 文本消息 | `header.event_type == "im.message.receive_v1"` | 按 `root_id`/`parent_id` 归到对应告警 |

文本消息**只认回在告警卡片话题下的消息**，群里的闲聊不会被当成回复；
`@_user_1` 这类 at 占位符会被剔掉再做意图识别。

意图识别：

- 认领：`帮我查`、`查一下`、`开始处理`、`排查`、`定位`、`diagnose` 等
- 拒绝：`我自己看`、`不用了`、`稍后`、`忽略`、`误报` 等
- **认不出就不猜**：回一句提示告诉人怎么答，状态不变

除鉴权失败和加密事件外，回调**一律回 200**——飞书对非 200 会重推。

### 3.4 状态机

```text
RECEIVED → NOTIFIED → AWAITING_REPLY ─┬─ CLAIMED → DIAGNOSING ─┬─ DIAGNOSED
                                      │                        └─ FAILED
                                      ├─ DECLINED
                                      └─ TIMEOUT → CLAIMED（人后来回了）
```

`AWAITING_REPLY` 和 `TIMEOUT` 都到不了 `DIAGNOSING`，必须先经过 `CLAIMED`——
「人必须点头」这条约束写死在状态机里，不靠调用方自觉。

超时（默认 600 秒无人认领）只做**升级提醒**：机器人再抬头一次、飞书催办一句。
`auto_diagnose_on_timeout` 默认 `false`——告警风暴下自动开跑会同时拉起 N 个 Claude Code，
既烧钱又会把 SAE 只读接口打满。

## 4. 硬件联动

| 时机 | 状态栏 | 表情 | 动作 | 播报 |
| --- | --- | --- | --- | --- |
| 告警到达（紧急/严重） | 线上告警 | `shocked` | `look_up` | 是 |
| 告警到达（警告） | 线上告警 | `confused` | `look_up` | 否 |
| 超时无人接 | 还没人接 | `shocked` | `look_up` | 是 |
| 人已认领 | 排查中 | `happy` | `nod` | 是 |
| 诊断进行中 | 排查中 | `thinking` | — | 否 |
| 诊断完成 | 排查完成 | `confident` | `nod` | 是 |
| 诊断失败 | 排查失败 | `sad` | `shake` | 是 |
| 人说自己看 | 待机 | `neutral` | `nod` | 否 |

表情只用固件已有的 21 种，动作只用既有预设（见 AGENTS.md「硬件边界」）。
**告警画面不会自动收回**——没人处理的告警一直挂在屏幕上，自动恢复等于把告警吞了。

播报文本只取根因的第一句（≤40 字）：OLED 是 128×64 单色屏，16px 中文一行约 8 字、
最多 4 行，整份诊断塞不进去。

## 5. 诊断子进程

实际命令（`command_preview()` 的输出，失败卡片里会附上供手工重跑）：

```bash
claude -p --output-format json --permission-mode dontAsk \
  --model <可选> --add-dir <被诊断服务源码目录> \
  --allowedTools Read Grep Glob Bash Skill TodoWrite
```

提示词走 **stdin** 而不是 argv：告警原文可能很长，Windows 命令行有 32K 上限，
且原文里的引号跨平台转义极易出岔子。

提示词里会明确声明**告警原文是不可信数据**：它来自线上日志，任何人只要能让一行文本进日志，
就能把内容送进这段提示词。实测真 CLI 会把「像指令的告警」识别成注入并拒绝诊断，
所以边界必须写在提示词里，把原文限定为「被诊断的对象」而非指令。

子进程环境里 `NO_PROXY` / `no_proxy` 会被追加 `iflytek.com`——
内网域名解析到 10.x，走代理必挂。

输出解析按「信封 → 结论」两层剥：先取 `--output-format json` 的 `result` 字段，
再从其中抠出第一个完整 JSON 对象（容忍代码围栏和前后闲聊），最后按 skill 的输出契约校验。
**契约破了就报失败**，把原文前 1200 字附在失败卡片里，绝不猜一个根因出来。

## 7. 失败模式

| 失败 | 表现 | 兜底 |
| --- | --- | --- |
| 机器人不在线 | `robot_delivered: false` | 飞书照发，卡片标注「机器人离线」 |
| 飞书发卡片失败 | `feishu_error` 有值 | 机器人照提醒，告警仍进入等待回复 |
| 依赖没配齐（CLI / skill / SAE 凭证） | `FAILED`，**秒级返回** | 失败卡片逐条列出缺什么、怎么补 |
| 诊断超时 | `FAILED` | 子进程被 kill（不 kill 会留下还在烧 token 的孤儿） |
| 输出不合契约 | `FAILED` | 附原文前 1200 字，不猜根因 |
| 两个人同时点「帮我查」 | 第二个人收到 `ALREADY_HANDLED` | 只跑一次诊断 |
